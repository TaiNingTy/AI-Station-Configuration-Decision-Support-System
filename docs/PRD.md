## 1. 背景与问题

自动驾驶公共交通站点的配置，长期依赖资深设计师的经验，运营、工程、设计三方标准不统一，方案反复返工，周期长、难复用。把表象抽象为三个**产品问题**：

1. **非结构化知识无法直接执行**——规范、约束、历史案例散落在文档和人脑里。
2. **工程/安全规则没有标准化决策入口**——规则靠人工解释，前后不一致。
3. **配置过程与决策依据无法复用、追溯**——换个项目就从头再来。

> 定位不是"缺一个聊天机器人"，而是"**缺一个标准化、可执行、可审计的决策工作流**"。

## 2. 目标 / 非目标 / 成功指标

**目标**：在不替代工程师最终决策的前提下，缩短合格方案产出时间、提升规则合规性与跨项目复用能力。

**非目标（本版本明确不做）**：完全自动设计、未经人工审核的工程输出、空间/GIS 深度分析与专有优化逻辑（见 Roadmap）。

**成功指标**：
| 指标 | 口径 |
|---|---|
| 推荐有效性 | 推荐配置被采纳/基本采纳的比例 |
| 规则合规性 | 硬约束校验通过率、无外部虚构规范 |
| 人工修改率 | 交付方案被人工改动的幅度 |
| 任务完成时间 | 从资料齐备到第一版可评审方案 |

## 3. 用户与核心场景

| 用户 | 关注 |
|---|---|
| 运营 | 服务能力、覆盖人群 |
| 工程 | 安全、可实施性、硬约束 |
| 设计 | 空间形态、体验 |
| 管理者 | 周期、成本、复用 |

**核心场景（MVP）**：设计师输入场地简报 → 系统产出一份 grounded、带依据与置信度、标注人工确认项的**站点配置交付草案**。

## 4. 范围与 MVP 边界

| 由谁负责 | 做什么 |
|---|---|
| **AI（LLM）** | 需求结构化、知识检索、初步配置、文档生成 |
| **确定性规则引擎** | 工程、安全、无障碍**硬约束**校验（PASS/FAIL）|
| **人（HITL）** | 最终配置、工程可实施性、商业/预算决策 |

## 5. 产品架构与功能需求（FR）

```
场地简报 → [Agent1 需求分析] → [规则门禁(代码)] →选择器
                                    ├ PASS → [知识库→Agent2 校验]→[Agent3 配置+文档]→交付草案
                                    └ BLOCKED → 风险与整改建议（不生成配置）
```

- **FR-1 需求分析（[Agent 1](../agents/01-requirement-analysis.md)）**：解析场地简报，判定站点等级(S/A/B/C)，抽取结构化字段（含 `curve_radius_m`、`platform_on_curve`）。输出 `requirement.json`。
- **FR-2 检索 + 规则校验（[Agent 2](../agents/02-rule-evaluation.md)）**：强制检索知识库（KB_01–04），做合规检查与风险识别；**只引用知识库、禁用外部规范、查不到输出"未覆盖"**。输出 `evaluation.json`。
- **FR-3 确定性规则门禁（[skills/rule-check.js](../skills/rule-check.js)）**：对硬约束（曲线半径<30m、直线站台段<8m、月台高差>20mm 无补偿）用**代码**判 PASS/FAIL；Critical FAIL → `BLOCKED`，**物理阻断下游配置生成**；缺失输入 → `NEEDS_REVIEW`（不放行）。
- **FR-4 配置 + 文档（[Agent 3](../agents/03-configuration-doc.md)）**：基于需求与校验结果，生成配置表（值/依据/置信度）、风险与人工确认项、交付 Checklist、设计说明。输出 `proposal.md`。
- **FR-5 人工复核（HITL）**：按风险分级触发——输入缺失、检索依据不足、规则冲突或硬约束不满足**必须转人工**；低风险且依据充分才继续自动生成草案。

## 6. 职责边界（核心设计原则）

> **软推理归 LLM（可容错）｜硬约束归代码规则（不可错）｜责任决策归人（有后果）。** 详见 [product-decisions.md](product-decisions.md)。

## 7. 非功能需求（NFR）

| 类别 | 要求 |
|---|---|
| Grounding | Agent 2 只引用知识库；来源可溯源到 KB_0x；无外部虚构标准 |
| 可追溯 | 每条结论可追溯到依据；提示词/模型/知识库/规则均有版本（见 [config/retrieval.yaml](../config/retrieval.yaml)）|
| 安全/权限 | 硬约束不由 LLM 决定；高风险交人工 |
| 可配置 | 规则库从硬编码升级为**按地区配置** |
| 可评估 | 关键链路可单节点评测；确定性层有可运行评估（[evals/](../evals/)）|

## 8. 评测与验收标准

以**可验证 PASS/FAIL 断言 + 真实用例**为主、定性维度为辅（详见 [evaluation.md](evaluation.md)）：
- JSON schema 合法、站点等级判定正确、关键规则命中、引用存在于 KB、无外部虚构标准、Critical FAIL 后阻断生成、报告章节完整、端到端耗时。
- 确定性门禁：`node evals/run.js` → 9/9。

## 9. 里程碑

| 阶段 | 目标 | 重点 |
|---|---|---|
| **Alpha** | 单场景核心链路跑通 | 规则先硬编码；证明"能否正确生成" |
| **Beta** | 加地区规则包 + 接空间/需求数据 | 证明"不同项目能否复用" |
| **UAT** | 运营/工程/设计共同验收 | 按四类指标验收，依修改记录优化规则与输入字段 |

## 10. 风险 / 依赖 / 开放问题

- **风险**：RAG 幻觉（已通过强制 grounding + 拒答机制缓解）；配置层数值为设计假设、需工程复核（非 KB 事实）。
- **依赖**：知识库质量与治理；多源空间数据接入。
- **开放问题**：完整 3-Agent 接到门禁 PASS 分支后（V1.2）；按 chunk 的引用 metadata；标定的置信度。

## 11. Roadmap

- **V1（本仓库）** 知识库 + agentic workflow 规则校验 + 配置推荐 + 人工复核交接
- **V1.1（已完成）** 确定性规则门禁部署并验证（物理阻断）
- **V1.2** 完整 KB→校验→文档 Agent 接到门禁 PASS 分支
- **V2** GIS/CAD 接入、需求预测、站点仿真 ｜ **V3** 优化引擎、自动迭代
