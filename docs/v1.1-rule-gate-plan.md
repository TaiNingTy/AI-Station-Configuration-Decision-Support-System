# V1.1 · Deterministic Rule Gate — Build Plan

Goal: hard constraints decided by **code**, and a **conditional branch** that physically blocks
configuration generation on a Critical FAIL — not a prompt asking the LLM to behave.

> **Why a Workflow, not the multi-agent Bot:** the 多 Agents Bot canvas only holds Agent nodes.
> Code nodes + conditional branches live in a Coze **工作流 (Workflow)**. So V1.1 is built as a Workflow.

---

## Target architecture (Coze Workflow)

```
开始 (site_info)
  → LLM1  需求分析        → requirement_json  (adds explicit: curve_radius_m, platform_on_curve)
  → Code  site-gate       → { workflow_status, allow_configuration, blocked_reasons }
  → 条件分支 (Selector)
        ├─ allow_configuration == true  →  知识库 → LLM2 规则校验 → LLM3 配置+文档 → 结束(proposal)
        └─ else (BLOCKED / NEEDS_REVIEW) →  LLM/输出: "需人工决策 / BLOCKED" + blocked_reasons → 结束(blocked report)
```

The `else` branch **never reaches LLM3**, so no deliverable configuration is produced. That is the real gate.

## Coze Code node — paste this (JavaScript)

Input params to map: `curve_radius_m` (Number), `platform_on_curve` (Boolean).
Output fields: `workflow_status` (String), `allow_configuration` (Boolean), `blocked_reasons` (Array).

```javascript
async function main({ params }) {
  const SITE_RULES = [
    {
      id: "ENG-006", name: "Curve radius", source: "KB_02",
      field: "curve_radius_m", threshold: 30, severity: "critical",
      reason: "曲线半径 < 30m，停靠精度不达标，不可实施",
      applicable: (p) => p.platform_on_curve !== false, // false → N/A
      compliant: (v) => v >= 30,
    },
  ];

  const check = (rule, p) => {
    const val = p[rule.field] ?? null;
    const base = {
      rule_id: rule.id, name: rule.name, source: rule.source,
      threshold_value: rule.threshold, actual_value: val, severity: rule.severity,
    };
    if (rule.applicable(p) === false) return { ...base, status: "NOT_APPLICABLE", reason: "规则不适用" };
    if (val === null || val === undefined) return { ...base, status: "NOT_EVALUATED", reason: `缺少 ${rule.field}，需人工补充` };
    const ok = rule.compliant(val, p);
    return { ...base, status: ok ? "PASS" : "FAIL", reason: ok ? "符合" : rule.reason };
  };

  const results = SITE_RULES.map((r) => check(r, params));
  const anyFail = results.some((r) => r.status === "FAIL");
  const anyUneval = results.some((r) => r.status === "NOT_EVALUATED");
  const workflow_status = anyFail ? "BLOCKED" : anyUneval ? "NEEDS_REVIEW" : "PASS";

  return {
    workflow_status,
    allow_configuration: workflow_status === "PASS",
    blocked_reasons: results.filter((r) => r.status === "FAIL" || r.status === "NOT_EVALUATED"),
  };
}
```

> This is the same logic as [`../skills/rule-check.js`](../skills/rule-check.js), reshaped into Coze's single-`main` node
> signature. The reference file keeps the two-phase API (`evaluateSiteConstraints` / `evaluateProposedConfiguration`)
> and full unit examples; the config-phase rules (platform length, accessibility gap) plug into a second Code node
> after LLM3 in Phase B.
